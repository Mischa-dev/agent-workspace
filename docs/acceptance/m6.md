## Accepted boundary

M6 adds one production-shaped MCP Streamable HTTP endpoint on the ordinary
private application listener, Project-scoped bearer credentials for
development, authorization code with PKCE for local Codex, bounded Project and
Work Item tools, optimistic replay-safe writes, Actor-attributed audit, an
unsent `codex://new` handoff, and a disposable-profile setup runbook.

MCP is another authorized client of the existing application domain. It does
not receive browser cookies, database access, hosted-provider credentials, or
client-supplied authorship. Connecting, reading, or writing through MCP creates
no Agent Workspace Conversation, Thread, Message, Agent Run, workspace,
branch, worktree, or provider session.

## Bearer acceptance

A one-day `read write` credential was issued on the host for the retained
human Actor and seeded Agent Workspace Project. Its plaintext was passed only
to a disposable local Codex process through the configured child environment;
the database retained only its digest and safe prefix.

Pinned Codex `0.146.0` negotiated MCP `2025-06-18` and read the live Project.
The same credential posted the bounded update
`M6 live MCP acceptance verified with pinned Codex 0.146.0.` to `AW-2`.
Replaying the exact request ID returned the original activity
`019fbeb5-9701-79d1-b59f-b87dae79de64` and result
`019fbeb5-9706-7f23-a898-0c759f92abf8` with
`idempotentReplay=true`; no Work Item version, activity, audit success, or
outbox record was duplicated.

A separate read-only credential could read but not write, then failed with
HTTP 401 immediately after optimistic revocation. A third credential failed
with HTTP 401 after controlled expiry. The final accepted release repeated the
read and exact replay, repeated both fail-closed probes, and then revoked every
disposable bearer credential. No active M6 bearer credential remains.

## OAuth and real Codex acceptance

The real pinned CLI used an isolated `CODEX_HOME`, public dynamic client
registration, exact loopback callback, authorization code, PKCE `S256`, state,
and explicit browser consent for the seeded Project and `read write` scopes.
The browser remained on the private SSH-forwarded application listener; the
callback returned only to a loopback port owned by the disposable CLI.

After login, Codex read `Agent Workspace` through `project_get`. An interactive
Codex TUI displayed the write approval for `work_item_post_update`; choosing
Allow posted
`M6 OAuth acceptance verified with pinned Codex 0.146.0.` to `AW-2` under the
authenticated human Actor. Exact replay reused activity
`019fbf21-5d6f-7313-89e1-55f2f56a5f04` and result
`019fbf21-5d74-7d51-a2d9-9a227ef3caff` with
`idempotentReplay=true`.

The first login used the macOS Keychain store and proved consent and tool use.
Codex's local token-expiry metadata could not be changed non-interactively
because macOS correctly required a Keychain prompt. A second login used
Codex's supported owner-only file credential store. After setting only its
local `expires_at` metadata to expired, the next real Codex invocation rotated
the refresh token and obtained a new access/refresh pair before successfully
calling `project_get`. PostgreSQL showed two access tokens, one used refresh
token, one new unused refresh token, and one unrevoked grant before cleanup.

Codex `mcp logout` removes local OAuth credentials but, in version `0.146.0`,
does not call the authorization server's revocation endpoint. Acceptance
therefore separately posted the current refresh token to `/oauth/revoke` over
stdin, received HTTP 200, observed the whole grant family revoked, and then
removed the local credential file. A subsequent required MCP startup failed
with `Auth required`. All four disposable public clients and both grant
families were left revoked; no live OAuth access or refresh token remains.

## Open in Codex acceptance

Chrome opened `AW-2` through the real Red Hat application, linked the retained
trusted spike repository as its primary repository, and enabled the Local
Codex handoff. The generated link had this bounded shape:

- scheme and target: `codex://new`
- `originUrl`: `https://github.com/Mischa-dev/agent-workspace-m0-spike.git`
- prompt: immutable Project ID and canonical URL, immutable Work Item ID and

webhook secret and no Mac, Red Hat, release, provider-profile, or worktree
path. Chrome triggered the external-protocol handoff while the task remained
prefilled and unsent. Linking the repository created one ordinary Actor-
attributed Work Item activity and advanced `AW-2` once from version 6 to 7.

## Exit decision

Every M6 exit criterion is satisfied against exact green commit
`d825c3ca267ce7ea2831b396feddedbf9c9b2793`. The active
`main-required-checks` ruleset continues to require the GitHub Actions `rust`
and `web` checks on `main`.

were corrected in the accepted release. Codex's local-expiry refresh behavior
and local-only logout behavior are external compatibility findings recorded in
`docs/compatibility/mcp.md`; server-owned grant revocation remains explicit and
fail-closed. The M7 Teams backlog and its identity decisions are elaborated in
pull request [#53](https://github.com/Mischa-dev/agent-workspace/pull/53). M7
is therefore authorized.
