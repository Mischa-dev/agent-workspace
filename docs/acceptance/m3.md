## Current boundary

This record covers the first production-shaped M3 slices: durable Execution
Worker, Provider Connection, Execution Profile, Repository, Repository
Workspace, Provider Session, and Agent Run ownership/admission foundations. It
does not claim that all M3 acceptance gates are complete. The bounded process
supervisor, account setup, repository registration, and managed Git runtime
are merged but have not yet been deployed on the Red Hat acceptance host.
Account ceremonies, repository preparation, scheduler, normalized
provider-event stream, recovery, frontend controls, or browser-driven hosted
run have not been accepted on Red Hat.

The foundation adds authenticated, Project-scoped status-only APIs for
Execution Workers and Execution Profiles. Browser DTOs expose fixed provider
capabilities, bounded status, Actor identity, optimistic versions, health time,
and redacted failure categories. They exclude `CODEX_HOME`, repository and
worktree paths, host identity, credentials, arbitrary provider JSON, and raw
errors.

## Supervisor slice verification

The `codex/m3-supervisor` slice replaces per-run process ownership in the
application path with one bounded, lazily initialized process per Execution
Profile. Sequential runs reuse the process while every turn still holds the
profile's single M3 lease. The process starts from a neutral data root and each
typed Thread or turn operation supplies its exact managed worktree. App Server
methods and raw JSON stay inside the adapter.

The slice adds typed limits for host profiles, JSONL lines, stderr, buffered
events, request timeouts, and shutdown; bounded restart backoff and a circuit;
ordered pre-response notification draining; strict response correlation;
whole-process-group termination; and coordinated application shutdown.
Production disables the spike's automatic approval behavior. Only the three
known approval methods and the user-input question method enter the durable
blocker path; every other provider request fails closed.

Deterministic supervisor tests initialize one fake App Server, buffer and
replay an event that arrives before its correlated response, start two
sequential Threads and turns through the same process, confirm the neutral cwd
and isolated `CODEX_HOME`, reject a second profile at the host limit, exercise
the circuit calculation, and shut the registry down. Authenticated profile
status returns only a redacted supervisor state and bounded counters.

Against a fresh disposable PostgreSQL database, the complete Rust workspace
suite passed with 98 server unit tests, all database/HTTP/realtime suites, 5 M3
foundation database tests, 1 M3 execution HTTP test, and every deterministic
spike test. Strict Clippy, formatting, `cargo deny`, `git diff --check`, and the
frontend lint, typecheck, 20-file/86-test Vitest suite, and production build
passed. The disposable database was dropped and zero temporary CI databases
remain. Pull request [#12](https://github.com/Mischa-dev/agent-workspace/pull/12)
then passed both required jobs in CI run
[`30666580074`](https://github.com/Mischa-dev/agent-workspace/actions/runs/30666580074)
and was squash-merged as `e88319d`. Red Hat process-reuse and shutdown evidence
remains open.

## Account setup slice verification

The account slice adds owner-authorized account status, browser login,
device-code login, explicit API-key login, cancellation, logout, and bounded
status polling beneath the Execution Profile resource. Mutations enforce an
authenticated private session, exact Origin, double-submit CSRF, Project and
profile ownership, authenticated write limits, and bounded idempotency keys.
Ceremonies are isolated to the initiating session, Actor, and profile, expire
after ten minutes, and cannot exceed the configured active-profile bound.

The provider adapter exposes only account type, optional email, bounded rate
limit windows, safe login URLs or user codes, and ceremony expiry. API keys are
zeroized after the adapter call and absent from durable state and response
types. Provider failures are reduced to an operator-safe category. Logout
changes admission state before stopping the supervisor, preserves run and
Thread history, and is safe to repeat.

## Durable scheduler and workspace admission verification

The scheduler branch makes authenticated run creation a bounded idempotent
command. It resolves immutable requesting Actor, Worker, personal Execution
Profile, and repository identity in one transaction; records the prompt and a
`queued` Agent Run; and returns only safe logical identifiers, queue position,
and nullable workspace context. Host paths are no longer returned. An explicit
repository must match an existing Thread binding, while an unbound Thread uses
the sole ready repository or receives a typed `repository_choice_required`
response with safe repository IDs.

Only the owned scheduler moves a run from `queued` to `starting`. Claims use a
30-second database lease, global scheduler serialization, creation-order
`FOR UPDATE SKIP LOCKED`, per-Profile exclusion, and the configured host
ceiling. Queued rows have no Repository Workspace or worktree. After admission,
the scheduler verifies the prepared canonical mirror, records the exact base
commit and collision-safe branch, creates the logical workspace, then creates
the UUID-scoped physical worktree. Failures retain inspectable database and
filesystem state. The provider turn ID is persisted before `working`.

Migration `0012_m3_agent_run_scheduler.sql` adds immutable predecessor identity
and bounded claim/lease state. Its SHA-384 is
`920bb1e1d4ad9e34e4af85c064c9ec603e90f88663d3b1b5cdffa299c0758a6ac6d3523dc7e59e4b90113c9efe091faa`.
The real-PostgreSQL scheduler flow proves idempotent replay and payload

## Provider event and blocker convergence verification

The provider adapter now derives bounded deterministic keys from provider item
identities, falling back to a SHA-256 identity when an upstream notification
does not carry a safe bounded identifier. Significant event insertion uses the
existing `(agent_run_id, event_key)` uniqueness boundary and allocates a
Conversation sequence only when the event is new. Replayed notifications
therefore cannot create duplicate timeline cards or invalidation events.

Migration `0013_m3_provider_event_idempotency.sql` enforces one consolidated
Worker Message per Agent Run and adds durable provider-response claim/delivery
checkpoints. Its SHA-384 is
`19096481ae9e96b3e04e7efa730ef24c4b3a06e250b6e1725cfd3c3b84a16562924a587ca7ef782cd3465340440c8af8`.
Provider approval/question requests converge on their existing
`(agent_run_id, provider_request_id)` row. A response is claimed once before
the adapter sends it; an ambiguous transport failure fails the run
conservatively instead of forwarding the same answer twice.

Questions are no longer projected as boolean approvals. The adapter retains
only a bounded prompt, safe choice labels, and question IDs, while the browser
accepts a bounded free-text or suggested-choice answer. The authenticated
response command validates the blocker kind, resolves the Actor server-side,
writes a `question_resolved` event without embedding answer text, and supports
the same bounded idempotent replay as approvals. The scheduler HTTP flow proves
question response/replay against real PostgreSQL, the migration test rejects a
second Worker Message and an unclaimed delivery, and the browser suite proves
the typed answer payload and absence of approval controls for a question.

The complete Rust, real-PostgreSQL, dependency, frontend, and production-build

## Explicit retry and conservative recovery verification

The authenticated retry command creates a distinct queued Agent Run with an
immutable `predecessor_run_id`, current Actor/Worker/Profile authorization
snapshot, the same Thread and Repository, and bounded idempotent replay. A
queued retry has no new workspace. At scheduler admission, a repository-scoped
Git inspection verifies the predecessor's exact mirror, branch, worktree, and
clean state before reusing its logical workspace. A dirty, missing, foreign, or
branch-mismatched worktree is never reset or rebound: the new run fails with an
actionable bounded reason while the predecessor branch and files remain in
place. The browser exposes retry only for the latest terminal run and keeps new
prompt submission as a separate action.

Startup reconciliation now treats queued work as scheduler-owned state rather
than attempting the invalid `queued` to `recovering` transition. It releases
abandoned short leases without creating filesystem/provider work. Started runs
still pass through `recovering`; recovery verifies the exact mirror and owned
branch before provider inspection, uses a stable recovery event identity, and
conservatively interrupts ambiguous state while preserving the worktree.

Real-PostgreSQL tests prove queued lease release, second-crash re-entry, clean
workspace reuse, distinct/idempotent retry creation, dirty retry rejection,
bounded failure state, and preservation of the uncommitted file. The browser
suite proves the stable explicit retry command. Pull request
[#17](https://github.com/Mischa-dev/agent-workspace/pull/17) passed the web job
in 1 minute 4 seconds and the Rust job in 8 minutes 18 seconds in CI run
[`30676181035`](https://github.com/Mischa-dev/agent-workspace/actions/runs/30676181035),
then was squash-merged as
`0529623c3dd1c1d8e3d3a5f5e6c97f7bc64e112c`. Deployment and systemd restart
acceptance remain open.

## Per-Actor failure acknowledgement verification

Migration `0014_m3_run_acknowledgements.sql` stores the Actor and the exact
durable `run_failed` event they saw, with same-Project membership foreign keys,
one acknowledgement per Actor and run, and a database trigger that rejects an
event belonging to another run or event kind. Its pre-merge SHA-384 is
`0d1aaacdf835b56bb77d3a1262087bab21db8eab4b9defc915d04d7639443f90b8e711b56e8893adcff75c9de4cb43b9`.

The acknowledgement command resolves Actor identity from the authenticated
session, requires the rendered durable failure event, enforces Project-scoped
read-state policy, and uses a resource-bound idempotency reservation. Timeline
and sidebar projections query the acknowledgement for the current Actor, so a
reload preserves one Actor's cleared failure while another Actor remains red.
The browser exposes an accessible text action and retains retry as a separate
choice. Real-PostgreSQL coverage proves replay creates one Actor-scoped row,
and browser coverage proves the exact event identity is sent and the action is
removed after convergence. This remains branch evidence until full gates, CI,
merge, and two-session HTTP isolation are complete.
