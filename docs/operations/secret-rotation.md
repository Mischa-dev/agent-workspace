# Secret rotation and revocation

This is the M8 private-host inventory and operator procedure. Secret values
never belong in the repository, shell history, process arguments, logs,
database projections, browser responses, or backup archives. Every candidate
file is created outside the checkout with owner-only permissions, validated in
place, and retained until the replacement is proven. Diagnostics identify only
the secret class, file path category, version, and success or failure.

## Inventory

| Class | Owner and storage | Consumers | Restart or overlap | Revocation proof |
| --- | --- | --- | --- | --- |
| PostgreSQL role password | `bot`/root and the rootless PostgreSQL project; connection URL in root-owned `/etc/agent-workspace/agent-workspace.env` | server and maintenance wrappers | coordinated database role plus environment cutover; verify a second connection before restart | old connection fails, new readiness succeeds, URL is never printed |
| GitHub App private key | GitHub App plus `/etc/agent-workspace/secrets/github-app.pem`, mode `0400`, owned by `agent-workspace` | installation-token client | GitHub supports more than one App key during cutover; content is read for each JWT, while path changes require restart | an installation-token diagnostic succeeds with the new key and fails after the old external key is removed |
| GitHub webhook secret | `/etc/agent-workspace/secrets/github-webhook-secret`, mode `0400`, owned by `agent-workspace` | webhook verifier only | optional previous file is activated with `AGENT_WORKSPACE_GITHUB_WEBHOOK_PREVIOUS_SECRET_PATH`; both signatures are accepted only for the bounded cutover | current signed delivery succeeds, then the previous signature fails after overlap removal and restart |
| Browser sessions | hashed session and CSRF values plus each User's authentication epoch in PostgreSQL | browser authentication and realtime session revocation | logout is immediate for one session; epoch increment revokes every session for one User | old cookie is unauthorized for HTTP and its WebSocket is closed or denied |
| Password credential | Argon2id PHC only in PostgreSQL; plaintext is interactive terminal input | login verifier | replace through the host-local interactive command and increment the User authentication epoch in one transaction | old password fails, new password succeeds, pre-rotation sessions fail |
| MCP bearer credential | one-time plaintext response; SHA-256 token hash and bounded prefix metadata in PostgreSQL | MCP authentication | optimistic replacement issues one successor and revokes the predecessor atomically | old bearer returns unauthorized; new bearer works within the same Project scope |
| MCP OAuth client and grant family | hashed client secret, authorization codes, access/refresh tokens, and grant state in PostgreSQL | OAuth endpoints and MCP authentication | client replacement or grant-family revocation; refresh-token reuse revokes the family automatically | old access/refresh material fails and no successor can be issued from the revoked family |
| Codex Execution Profile | isolated `CODEX_HOME` below `/var/lib/agent-workspace/codex/profiles`; owned by its human User | one profile supervisor and its runs | use the application `account/logout` path, then the ordinary browser/device login ceremony; never copy a profile | account state is logged out/authentication-required, run admission fails, then the intended account is shown after login |
| Backup encryption material | none selected for the ordinary owner-local M8 backup | none | if later introduced, it is operator-owned and external to Agent Workspace | absence is explicit; no placeholder or recovery key is generated by the application |

## File-backed secret preflight

Run from a root-capable `bot` session. Candidate files must be absolute regular
files outside the checkout, releases, application data, and backup roots. Do
not place a value directly in a command.

```bash
sudo stat -c '%a %U:%G %s %n' /absolute/path/to/candidate
sudo test -f /absolute/path/to/candidate
sudo test ! -L /absolute/path/to/candidate
```

The private key is at most 64 KiB and is checked without displaying it:

```bash
sudo openssl pkey -in /absolute/path/to/candidate -check -noout
```

A webhook candidate is at most 4 KiB and contains at least 32 bytes. The
checked-in installer validates its class, path components, file type,
permissions, size, and private-key structure where applicable; it stages the
candidate in the destination directory and atomically renames it. The
superseded known-good candidate remains in its separate owner-only operator
location until post-cutover verification passes.

```bash
sudo /opt/agent-workspace/current/bin/install-file-secret.sh \
  github-webhook-current /absolute/path/to/candidate
```

If validation or `install` fails, do not rename anything. If health or the
external diagnostic fails after rename, atomically reinstall the retained
known-good candidate and restart. The accepted classes are
`github-app-private-key`, `github-webhook-current`, and
`github-webhook-previous`; arbitrary destinations are never accepted. The
installer removes its exact `.next` file after any interrupted attempt.

## GitHub webhook current-plus-previous cutover

1. Copy the current file to
   `/etc/agent-workspace/secrets/github-webhook-secret.previous` with owner
   `agent-workspace`, group `agent-workspace`, and mode `0400`.
2. Add only the path below to the root-owned environment file and restart:

   ```text
   AGENT_WORKSPACE_GITHUB_WEBHOOK_PREVIOUS_SECRET_PATH=/etc/agent-workspace/secrets/github-webhook-secret.previous
   ```

3. Confirm readiness and one delivery signed with the still-current secret.
4. Change the development GitHub App to the new candidate, then atomically
   replace only `github-webhook-secret`. The verifier checks both bounded files
   without logging which one matched.
5. Confirm a newly signed delivery, repository identity, and delivery
   deduplication. Retain the old file only long enough to cover the external
   cutover.
6. Remove the previous-path environment line, restart, and prove a fixture
   signed with the old value receives the bounded signature failure. Only then
   remove the exact `.previous` file and the external candidate copies.

The overlap is never a general key ring, has no automatic extension, and is
not accepted when either configured file is missing, unsafe, empty, or too
large.

## Other supported ceremonies

- MCP: use `mcp-credential-replace` with the current credential UUID and
  optimistic version. Capture the successor plaintext once, update the one
  client, verify it, and prove the predecessor is rejected. Use
  `mcp-credential-revoke` when no successor is required.
- OAuth: revoke the exact client/grant through the authenticated OAuth revoke
  path. Never edit token rows. A reused refresh token is treated as a family
  compromise and the whole family remains revoked.
- Browser password and sessions: run the host-local interactive command below.
  It replaces the PHC, revokes active session rows, advances the authentication
  epoch, and writes one Actor-attributed audit event transactionally; plaintext
  never appears in argv or JSON output.

  ```bash
  sudo /opt/agent-workspace/current/bin/agent-workspace-service-command \
    user-password-rotate --login-name '<login-name>'
  ```
- Provider: verify the selected profile belongs to the intended human, invoke
  profile logout, confirm run admission is denied, and complete the ordinary
  browser or device ceremony. Never duplicate or export `CODEX_HOME`.

## PostgreSQL coordinated password cutover

Take and validate an ordinary backup first. Create the candidate password in an
owner-only root file, never a variable or argument. Open a second local
connection using a temporary owner-only connection file and verify
`current_database()` plus the expected role. Update the root-owned application
environment through a same-directory temporary file and atomic rename, restart
the application, and require readiness plus a maintenance query before closing
the old known-good connection. If either check fails, restore the retained
environment file and restart. Only after success may the old credential and
temporary file be removed. Do not print `AGENT_WORKSPACE_DATABASE_URL`, use
manual SQL row edits, or attempt an old-code rollback across an incompatible
migration.

## Redaction canary gate

Before and after a live ceremony, place a unique canary only in an owner-only
file. Scans use the file as a pattern source and suppress matching content:

```bash
sudo journalctl -u agent-workspace.service --since '15 minutes ago' \
  | sudo grep -F -q -f /etc/agent-workspace/rotation-canary \
  && echo 'FAIL: canary detected' \
  || echo 'clear'
```

Repeat the bounded check against exported safe database projections, captured
browser response metadata, and the allowlisted provider-environment key list;
never scan by putting the canary in SQL text, a URL, or argv. Record only
`clear` or the affected category. After the old material is proven rejected,
remove the exact temporary candidate, canary, and overlap files and state that
they are no longer recoverable unless retained by the external provider.

## Secrets keyring (encrypted secrets)

Keys people save in the app (provider API keys) and the server's own signing
secrets are stored encrypted (`secrets.rs`): each with its own data key,
sealed with AES-256-GCM, and the data keys sealed under a master key from the
keyring file named by `AGENT_WORKSPACE_SECRETS_KEY_PATH` (owner-only, outside
the data and release roots).

- Create it once, in a directory only the service account owns (the
  service reads the keyring, and rotation writes its replacement beside it):

  ```bash
  sudo install -d -o agent-workspace -g agent-workspace -m 0700 /etc/agent-workspace/secrets
  sudo /opt/agent-workspace/current/bin/agent-workspace-service-command \
    secret-key-init --path /etc/agent-workspace/secrets/keyring
  ```

  Then add `AGENT_WORKSPACE_SECRETS_KEY_PATH=/etc/agent-workspace/secrets/keyring`
  to `agent-workspace.env` with `sudoedit` and restart. On start, agent webhook
  secrets still stored in plaintext move into the store. Don't run
  `secret-key-init` as root directly: the file would be root's and the service
  couldn't read it.
- Rotate: `sudo /opt/agent-workspace/current/bin/agent-workspace-service-command secret-key-rotate`.
  It writes a new first key, re-seals every data key under it while the
  server keeps running, and removes keys nothing uses. Back the keyring up
  again afterwards (`agent-workspace-backup-key` does this when the file
  changes).
- Back it up apart from database dumps (docs/operations/backups.md): a dump
  and its keyring together are the plaintext.
- In development without the variable, the server creates
  `.agent-workspace-secrets/dev.keyring` in its working directory.
