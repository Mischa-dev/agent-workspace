## Accepted boundary

M5 adds Project-scoped GitHub App installation state, verified and deduplicated
webhook receipt, durable leased jobs, short-lived installation-token API and Git
operations, explicit publication of an exact clean worktree commit, durable pull
request creation and links, canonical checks and review projections, manual
refresh, and the two fixed Work Item automation rules. Opening a pull request to
Review remains disabled by default; merging an explicitly linked pull request
to Verification is enabled by default and still passes through the Project's
ordinary workflow transition graph.

GitHub remains the code-review system. Agent Workspace stores only bounded
identity and status projections, never diffs, logs, annotations, review bodies,
comments, webhook bodies, private keys, webhook secrets, or installation
tokens. Cleanup never force-pushes, resets, or deletes dirty worktrees.

The live acceptance exposed four gaps despite green pre-acceptance CI.
First, GitHub's pull-request REST projection returned a null merge commit after
the merged head branch had been deleted even though the signed close delivery
contained the exact merge commit. Decision D-047 and migration `0026` retain a
bounded signed fallback only on the checksum-verified delivery while preserving
the original job identity and payload. Once that identity is canonical, pull
request #43 also permits a later authenticated refresh to retain it when REST
again returns null; a non-null mismatch and every unmerged request still fail.
Second, the automation update referenced
a nonexistent M4 Work Item column. Pull request #42 removed that reference and
bound the schema-sensitive update behind a focused regression test. Actor
attribution remains on the activity, automation-result, and audit rows.
Third, the Work Item page exposed an obsolete nested-Channel Thread URL. Pull
request #44 switched the projection to the canonical Project Thread route and
added a real-PostgreSQL HTTP assertion for the exact generated link.
Fourth, Project-location synchronization used the broad `projects` query-key
prefix and treated a Work Item repository-picker cache as a Project list. The
navigation write committed, but the client then displayed a false failure.
Pull request #45 scopes navigation cache work to rail/search Project lists and
preserves the colliding repository-picker fixture in its regression test.

## Exit decision

Every M5 exit criterion is satisfied against the exact green commit. The M6
Local Codex and MCP backlog is elaborated separately in pull request
[#40](https://github.com/Mischa-dev/agent-workspace/pull/40). M6 is therefore
authorized. The active `main-required-checks` repository ruleset requires the
GitHub Actions `rust` and `web` checks on `main`. The REST merge-projection
assumption was invalidated during live acceptance and is recorded in Decision
D-047; the Work Item column reference
and obsolete Thread link were implementation defects and did not change an
architectural decision. The frontend query-key collision was likewise a cache
namespace defect, not a change to Project navigation ownership or durability.
